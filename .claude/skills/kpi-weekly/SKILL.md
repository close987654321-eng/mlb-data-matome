# kpi-weekly（週次KPIダイジェスト）

目的：「何が効いたか」を勘から数字にする。村山さんの可処分時間は週数時間＝**読んで1分・
判断材料になる1枚**だけを届ける。ダッシュボードではなく「今週の通信簿＋来週の一手」。

> 位置づけ: CLAUDE.md §8 の自動化スキル第1弾。X依存（流入67%スタート）から
> 検索/Discover への構成変化を毎週定点観測するのが最大の任務。

---

## 発動条件

- **自動**: 毎週月曜 07:00 JST のクラウド定期実行（ルーティン化の手順は references/setup.md §3）
- **手動**: 「今週のKPI」「先週どうだった」「KPIまとめて」

## Step 1: 数字を取る（両店）

```bash
# 1号店（MLB海外の反応）— .env.local の既定値で取れる
node scripts/fetch-kpi.mjs weekly --json

# 2号店（Japan Reacts / matome-anime）— env 上書きで同じスクリプトを使う（コピーを作らない）
GA4_PROPERTY_ID=541564295 GSC_SITE=sc-domain:matome-anime-kaigai.jp node scripts/fetch-kpi.mjs weekly --json
```

- プロパティIDのメモ: 1号店=541315640（海外の反応）/ 2号店=541564295（アニメまとめ）。
  数値はアカウントID（397718724）ではなく**プロパティID**を使う（間違えると403）。

- GA4（昨日までの7日間 vs その前7日）と GSC（遅延を見て3日前終わりの7日間 vs その前7日）が
  1つの JSON で返る。`warnings` に取得失敗が入る。
- **片方だけ取れた場合はある分だけで出す**。両方失敗（exit 1）なら「今週は計測不能」と
  その理由（スクリプトのエラーメッセージ）だけを報告して終わる。粘って数字をでっち上げない。
- GSC が 403/404 のときはサイト表記ズレの可能性 → `node scripts/fetch-kpi.mjs sites` で
  登録済みプロパティを確認し、`.env.local` の `GSC_SITE` を直す（初回だけの作業）。

## Step 2: 手貼りデータを合わせる（あれば・なくても出す）

- **X アナリティクス**（API取得不可・過去バン履歴により自動化しない）: ユーザーが数字を
  貼ってくれた場合（インプ・フォロワー増・伸びたポスト）だけ「X実測」欄に含める。
  クラウド実行時は前週DMへの返信があればそれを読む。**無ければ欄ごと省略**（空欄で出さない）。
- **note**（らく側）: 同様に貼られたときだけ。

## Step 2b: ストックの死活チェック（1号店・30秒）

```bash
node scripts/check-dead-videos.mjs
```

公開後に元動画が YouTube から消えると、記事の埋め込みか出典（送客先）が壊れる。放置すると
「出典の無いコメント転載」に見え、AdSense の有用性判定に直結する。**数字を見るついでに毎週1回、
ストックの腐りも見る**（2026-08-13 の初回検査で 526本中 2本が死亡）。

- 死亡ゼロなら**ダイジェストには書かない**（無風を報告しない）。1本でもあれば健康欄に1行足す
- 手当ての手順は [`scripts/check-dead-videos.mjs`](../../../scripts/check-dead-videos.mjs) 冒頭の
  コメントが正（A=記事を撤去して `data/deleted-ids.json` に積む／B=`sourceRemoved` を立てる）。
  **その場で直さず、ダイジェストに載せて村山の判断を待つ**（記事削除は不可逆）
- `YOUTUBE_API_KEY` が無い環境（クラウド実行でシークレット未設定）は exit 2 で止まる。
  その場合は**このステップだけ飛ばして先へ進む**＝KPI ダイジェスト自体は落とさない
- 2号店は revenue-weekly（土曜・ローカル）の Step 4 が同じ検査を担当する。ここで二重に回さない
  （このルーティンのチェックアウトに 2号店のリポジトリは無い）

## Step 3: ダイジェストを組む（この順・この分量で固定）

```
📊 週次KPI {開始}〜{終了}

① 今週の数字（先週比）
   セッション {n} ({±x%}) / PV {n} ({±x%}) / エンゲージ率 {x%}
② 流入源の構成
   Top5 と先週比。X依存率（t.co 系 ÷ 全体）の推移を必ず1行。
③ 🔥 Discover 監視
   impressions が 0→正 に変わった週は最優先で叫ぶ（着火＝戦略の転換点）。
   未点火なら「未点火（imp 0）」と1行だけ。web検索は click/imp/掲載順位を先週比で。
④ 記事の勝敗
   PV Top3（1行ずつ・伸びた理由の仮説を1行）。検索クエリTop5 は「拾われ方」が
   変わった時だけ載せる。
⑤ カードループ
   card_open→card_share/copy→utm_source=card 来訪の3段ファネル（先週比）。
⑥ 2号店（Japan Reacts）
   セッション/PV（先週比）・流入源Top3・GSC click/imp・Discover の4行だけ。
   カード/選手ハブ欄は1号店固有なので出さない。1号店と比べて特筆すべき動き
   （例: 検索流入の逆転）があれば1行添える。
⑦ 来週の一手（1個だけ・両店通算で）
   数字から導ける提案を1個に絞る。複数提案しない。「なぜそれか」を2行以内で。
```

- 数字は**必ず先週比**を添える。絶対値だけの数字は判断材料にならない。
- **事実と仮説を書き分ける**。仮説には「〜と推測」を明記。
- 全体で Slack DM 1通（目安30行以内）。長い分析は求められた時だけ。

## Step 4: 届ける

- クラウド実行時: Slack DM で送信（jp-games ルーティンと同じ宛先）。
- 手動実行時: チャットにそのまま出す。ファイルには保存しない（履歴は Slack スレッドが担う。
  リポジトリを計測ログで汚さない）。

## 絶対ルール

- **捏造・補間の禁止**: 取れなかった数字は「取得失敗（理由）」と書く。前週の値で埋めない。
- **サイト本体から API を叩かない**: 取得は本スクリプト（編集時/CI と同じ posture）のみ。
- **サービスアカウントの JSON キーをコミットしない**: `.env.local`（ローカル）と
  クラウドシークレットのみ。setup は references/setup.md。
- **来週の一手は1個**: 迷ったら「X依存率を下げる方向」を優先（生命線が単一障害点のため）。
